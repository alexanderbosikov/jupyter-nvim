# jupyter.nvim — архитектура

Создано 03.09.2026. Источник требований — `nvim-notebook-plugin.md` (идея, первопричина, тест-лист).
Здесь только конструкция: закрытые развилки, границы, протокол, модули, форматы, порядок сборки.

Этот файл переезжает в репозиторий плагина как `ARCHITECTURE.md`. Ссылки вида «§4.3 идеи» — на файл идеи.

**Имена (решено 03.09.2026).** Плагин `jupyter.nvim`, Lua-рут `lua/jupyter/`, команды `:Jupyter*`,
сайдкар — пакет `jupyter_nvim` (не `jupyter`: `import jupyter` уже занят метапакетом), CLI — бинарник
`jupyter-out`, который `jupyter_core` подхватывает как подкоманду родного CLI: `jupyter out <file> <cell-id>`.
Осторожно: на ядре живёт `nb_utils` — это разные вещи (ядро vs редактор).

**Что держит переименование дешёвым** — свойство легко потерять, поэтому зафиксировано здесь:
маркер в тексте ноутбука нейтральный (`cell-id:`, без имени плагина), поэтому уже написанные ноутбуки
переименование не трогает; каталог выводов — опция конфига `out_dir`, а не константа. Всё остальное
(пути модулей, команды, имя пакета) — один sed. Дорожает только после публикации, когда имя попадёт
в чужие lazy-спеки.

## 1. Закрытые развилки (было §11 идеи)

| развилка | решение | почему | чем платим | когда пересмотреть |
|---|---|---|---|---|
| транспорт | **`vim.system` + JSON-lines по stdin/stdout** | сайдкар становится обычным процессом → приёмка гоняется из терминала без nvim (см. §9). Это главный аргумент, важнее типизированных вызовов | корреляция запрос↔ответ руками (реализована один раз в `sidecar.lua`, ~40 строк) | если понадобятся синхронные вызовы из статуслайна/`omnifunc` — тогда `remote#host#Register` как у dbee |
| где состояние ячеек | **в Lua** | сайдкар почти stateless: соединение + таблица маршрутизации. Одно место истины при рестарте | ядро не переживает рестарт nvim (v1) | когда захочется reattach к живому ядру по connection-файлу — состояние ядра уедет в сайдкар, состояние ячеек останется в Lua |
| границы ячеек | **регекспы за интерфейсом детектора** | `%%sql`-injections уже есть, регекспы работают; интерфейс делает treesitter заменой одного модуля | краевые случаи (фенс в строке, вложенный фенс) | после обкатки, если краевые случаи реально встретятся |
| вывод: drawer или буфер на ячейку | **один drawer на ноутбук + однострочный virt_text-статус под ячейкой** | сохраняет выигрыш §4.3 идеи, не размножает окна | нельзя видеть вывод двух ячеек одновременно | если станет мешать — drawer уже абстрагирован в `ui/common`, второй режим добавляется поверх |
| стабильный id ячейки | **короткий хэш в тексте**: `# %% cell-id: a3f9` / в info-строке фенса | id переживает перезагрузку буфера и находится grep'ом извне (требование §4.6 идеи) | первый запуск ячейки правит буфер (одна undo-able правка) | — |
| python для сайдкара | **путь из конфига**, по умолчанию — поиск venv `jupyter-utils` | там уже есть `jupyter_client` и polars; упаковка не блокирует v1 | нет изоляции зависимостей | когда плагин пойдёт кому-то ещё — свой venv под `stdpath("data")` |

## 2. Процессы и потоки данных

```
┌─────────────────── nvim ───────────────────┐
│  buffer (.md/.py, jupytext)                │
│  extmarks ── cell_id ── virt_text статус   │
│  drawer (scratch buffer)                   │
│              lua/jupyter/*                      │
└───────────────┬────────────────────────────┘
                │ JSON-lines (stdin/stdout)
                │ запросы ↓   события ↑
┌───────────────┴────────────────────────────┐
│  jupyter_nvim (python)                       │
│  jupyter_client · router(msg_id) · polars  │
└───────────────┬────────────────────────────┘
                │ ZeroMQ (shell/iopub/stdin/control)
┌───────────────┴────────────────────────────┐
│  ipykernel (jupyter-utils)                 │
└────────────────────────────────────────────┘

              .jupyter-out/<notebook>/   ← пишет сайдкар, читают: drawer (через сайдкар), CLI `jupyter out`, агенты
```

Три канала, и это осознанно:
- **запросы** — Lua зовёт сайдкар (execute, interrupt, страница таблицы);
- **события** — сайдкар пушит наверх (stream, result, done, состояние ядра);
- **диск** — тяжёлые данные (таблицы, картинки) не идут через пайп вообще, только пути к файлам.

## 3. Границы ответственности

Доктрина dbee (`ARCHITECTURE.md`: «clearly defined borders, not leak responsibilities»), приложенная сюда.

**Lua знает:** буферы, ячейки, extmarks, окна, клавиши, `run_id`, историю прогонов в памяти, ширину колонок
при отрисовке таблицы.
**Lua не знает:** ZeroMQ, структуру jupyter-сообщений, mime-бандлы, polars, parquet.

**Python знает:** протокол ядра, `parent_header.msg_id`, mime-бандлы, polars/parquet, layout `.jupyter-out/`.
**Python не знает:** номеров строк, буферов, окон, extmarks, что такое «ячейка в тексте». Для него ячейка —
только строка `cell_id`, пришедшая от Lua.

Практический тест границы: сайдкар должен полностью работать из `echo '{...}' | python -m jupyter_nvim`.
Если для какой-то фичи это перестаёт быть верным — граница протекла.

## 4. Протокол

JSON-lines: одна JSON-строка на сообщение, UTF-8, `json.dumps` без переводов строк внутри. Версия — `v`,
несовпадение валится на `hello` громко, а не тихо в рантайме.

### 4.1. Конверт

```json
// Lua → сайдкар (запрос)
{"v": 1, "id": "7", "op": "execute", "args": {"cell_id": "a3f9", "run_id": 12, "code": "..."}}

// сайдкар → Lua (ответ на запрос: есть id)
{"v": 1, "id": "7", "ev": "ok",    "data": {"msg_id": "3f2c..."}}
{"v": 1, "id": "7", "ev": "error", "data": {"code": "kernel_not_ready", "msg": "..."}}

// сайдкар → Lua (событие: id нет)
{"v": 1, "ev": "stream", "cell_id": "a3f9", "run_id": 12, "data": {"name": "stdout", "text": "..."}}
```

`id` — счётчик Lua, только для корреляции. Ответ на запрос всегда ровно один.

### 4.2. Запросы

| op | args | ok.data | примечание |
|---|---|---|---|
| `hello` | `{v}` | `{v, caps[], python, versions{}}` | первым делом; несовпадение `v` → плагин не стартует и говорит почему |
| `kernel.start` | `{kernel_name, cwd, env{}, notebook?, out_dir?, history_limit?}` | `{kernel_id, connection_file, kernel_name}` | `env` — сюда уезжает `NB_UTILS_ITABLES=0`. `notebook` включает запись в `.jupyter-out/`; без него сайдкар работает без диска |
| `kernel.state` | — | `{state, since_ms}` | `starting\|ready\|busy\|dead` |
| `kernel.restart` | `{}` | `{kernel_id}` | все `active_executions` закрываются как `aborted` |
| `kernel.shutdown` | `{}` | `{}` | |
| `execute` | `{cell_id, run_id, code, result_expr?}` | `{msg_id}` | отказ, если `state != ready\|busy` — гард из §12 п.1 идеи встроен в конструкцию. `result_expr` — что сериализовать в parquet, дефолт `_`; для `%%sql` Lua присылает имя переменной (§7.1) |
| `interrupt` | `{}` | `{}` | control-канал; ожидаем `aborted`-реплаи по остальной очереди |
| `stdin.reply` | `{value}` | `{}` | ответ на `ev: input_request` |
| `table.page` | `{path, offset, limit, cols[]?}` | `{header[], rows[][], total_rows, truncated}` | `pl.scan_parquet(...).slice(...)`; значения — уже строки, выравнивание за Lua |
| `ping` | — | `{}` | healthcheck |

Не в v1: `complete`, `inspect`, `history` (автокомплит по ядру — отдельная фича).

### 4.3. События

| ev | поля data | когда |
|---|---|---|
| `exec.started` | `{msg_id, started_at}` | ядро приняло `execute_request` (`status: busy` с нашим родителем) |
| `stream` | `{name, ops[]}` | `stream`-сообщение; `\r`/`\b`/ANSI уже применены (§6.3). `ops` — список `{op, text}`, где `op`: `append\|replace_last`. Список, а не строка, потому что один `\r` в потоке превращается в перерисовку строки, и решать это должен не UI |
| `display` | `{kind, mime?, path?, text?}` | `display_data`/`update_display_data`; картинка пишется файлом, в событии — путь |
| `result` | `{kind, path?, text?, has_html?}` | `execute_result`; `kind`: `text\|table\|image\|html\|unsupported` |
| `exec.error` | `{ename, evalue, traceback[]}` | `error`-сообщение; ANSI из трейсбека снят |
| `exec.done` | `{status, duration_ms, execution_count, user_expressions?}` | пришли **и** `idle`, **и** `execute_reply` (см. ниже); `status`: `ok\|error\|aborted` |
| `clear_output` | `{wait}` | ячейка попросила очистить вывод (tqdm, повторный рендер) |
| `input_request` | `{prompt, password}` | ядро спросило `input()` |
| `kernel.state` | `{state, reason?, implementation?, language_version?}` | смена состояния, включая смерть ядра |
| `orphan` | `{parent_msg_id, msg_type}` | родитель указан, но нам неизвестен — **аномалия маршрутизации**, логируется, не применяется |
| `log` | `{level, msg}` | диагностика сайдкара; `level: kernel` — вывод самого ядра без родителя (баннеры, предупреждения на старте) |

Любое событие может нести `late: true` — прогон, к которому оно относится, уже закрыт (§4.4).
Отдельного типа события для этого нет намеренно: Lua решает, показать ли такое с пометкой или спрятать.

**Прогон закрывается по двум концам.** `idle` приходит по iopub, а `execute_reply` со статусом — по shell.
Это разные каналы, порядок доставки между ними не гарантирован, а статус ошибки живёт только в реплае.
Поэтому `exec.done` уходит, когда получены оба. Исключение — `status: aborted`: своего `idle` такой прогон
не получит никогда, он закрывается сразу.

### 4.4. Два ключа вместо одного: зачем `run_id`

`cell_id` отвечает на «к какой ячейке», `run_id` — на «к какому прогону». Без второго ключа вывод, прилетевший
из фонового потока после `idle` (у нас реально есть: `nb_utils/notify.py` печатает из `threading.Timer`),
приезжает в панель уже второго запуска той же ячейки. Оба ключа едут в каждом событии; Lua отбрасывает всё,
где `run_id` не равен текущему для этой ячейки, и пишет такое в лог.

`run_id` выдаёт Lua (монотонный счётчик на буфер) — так он не теряется при рестарте сайдкара.

**Чего маршрутизация по `msg_id` не лечит (проверено на ipykernel 7.3.0).** Формулировку «баг из §1 идеи
невозможен по конструкции» надо читать узко: она верна для путаницы *на стороне клиента*. Но есть третий
механизм, кернел-сайдный:

| когда фоновый поток печатает | что ставит ipykernel в `parent_header` | что видим мы |
|---|---|---|
| ничего больше не выполняется | msg_id уже закрытой ячейки | правильная ячейка, `late: true` — **работает** |
| выполняется **другая** ячейка | msg_id текущего запроса | вывод приезжает в чужую ячейку, и отличить его нельзя |

Второй случай не лечится никаким клиентом: ядро само приписало сообщение не той ячейке. У Jupyter Lab
поведение точно такое же. Практический вывод для нас: `nb_utils/notify.py` печатает из `threading.Timer` —
если это совпадёт с выполнением другой ячейки, текст уедет к ней. Чинить надо на стороне `nb_utils`
(не печатать из фонового потока), а не здесь. Поведение зафиксировано тестом
`test_background_output_is_stolen_by_the_running_cell`, чтобы изменение в ядре не прошло незамеченным.

### 4.5. Инвариант маршрутизации

`active_executions: dict[msg_id, (cell_id, run_id)]` в сайдкаре — единственный источник привязки.
FIFO выводов нет нигде — ни в Lua, ни в Python. Именно это исключает путаницу на стороне клиента
(про границу этого утверждения — §4.4).

Сообщения не из таблицы делятся на три разных случая, и смешивать их нельзя:

- **`parent_header.msg_id` указан, но неизвестен** → `ev: orphan`. Настоящая аномалия: логируем, не применяем.
- **`parent_header` пустой** → это вывод самого ядра, а не ячейки: баннеры и предупреждения на старте
  (например «Kernel is running over TCP without encryption»). Уходит наверх как `log` уровня `kernel` —
  показать надо, аномалией не считать.
- **служебное**: `status` и `iopub_welcome` (без родителя по своей природе), `execute_input` (эхо кода),
  сообщения нашей собственной пробы stdin из §6.2 — молча игнорируются.

### 6.2. Готовность ядра — не через `wait_for_ready`

Второй механизм из §1 идеи: `wait_for_ready(timeout=0)` (а) сыплет `kernel_info_request`, каждый со своей
парой busy/idle в iopub, и (б) при успехе **дренирует весь iopub**, унося вывод уже запущенных ячеек.

`wait_for_ready` не вызывается никогда. iopub читается одним циклом, единственным потребителем.
До готовности состояние `starting`, и `execute` отклоняется с `kernel_not_ready` — гард встроен
в конструкцию, а не прикручен сбоку, как мост из §12 п.1 идеи.

Но «ответ на shell» готовностью **не является**. Выяснилось экспериментально при написании тестов:
ядро говорило `ready`, `execute` уходил — и ни одного события в ответ, либо первая половина вывода
терялась. Каналы разные, и каждый становится рабочим в свой момент:

| канал | тип сокета | чем доказывается готовность |
|---|---|---|
| shell | DEALER→ROUTER, надёжный, с очередью | ответ на наш `kernel_info_request` (свой `msg_id`) |
| iopub | **PUB/SUB** | любое полученное сообщение. Всё, что ядро опубликовало до установки подписки, потеряно безвозвратно — «медленный подписчик» ZeroMQ. Обычно первым приходит `iopub_welcome` |
| stdin | DEALER→**ROUTER на стороне ядра** | подтверждённый round-trip (см. ниже). ROUTER не может маршрутизировать к identity, которая ещё не подключилась, и `input_request` в это окно теряется молча. Измеренное окно — 50–300 мс, зависит от нагрузки |

Готовность = все три. Пока iopub молчит, `kernel_info_request` переспрашивается каждые 150 мс: его пара
`status` и докажет, что подписка жива. В отличие от `wait_for_ready` это безопасно, потому что (а) iopub
не дренируется, (б) цикл кончается на первом же полученном сообщении, (в) лишние `status` отсекаются
роутером по чужому родителю.

**Этапы готовности последовательны, и это не косметика.** Сначала ядро доказывает, что его главный цикл
жив (ответ на shell + живой iopub), и только потом мы имеем право посылать ему скрытые ячейки и тем более
`interrupt`. Наоборот нельзя: SIGINT, прилетевший в ядро, которое ещё импортирует модули, обрывает его
собственный старт — под нагрузкой это давало `KeyboardInterrupt` в трейсбеке `ipykernel_launcher` и ядро,
которое не поднималось никогда. По той же причине на второй этап уехало внедрение помощника из §7.1.

**Маршрут stdin подтверждается настоящим `input()`, а не сном.** Скрытая ячейка
(`silent=True`, `store_history=False`) вызывает `input()` внутри `except BaseException: pass`; приход
`input_request` и есть доказательство маршрута, мы отвечаем на него пустой строкой. Не пришёл за 400 мс —
ядро висит в ожидании, снимаем `interrupt` (его глотает `except`) и пробуем снова, до 10 раз.

Тупиковый путь, который важно не повторить: заранее послать пустой `input_reply`, чтобы ROUTER узнал нашу
identity. Работает в 4 случаях из 5, а в пятом приходит **в зазор между `input_request` и ожиданием ответа**,
и ядро принимает его за ответ пользователя: `input()` возвращает пустую строку. Зависание превращается
в молча неверные данные — это хуже. `ipykernel` дренирует stdin перед ожиданием, но только *перед*.

### 6.3. `\r` и `\b`

Обрабатываются в `stream.py`, а не в UI: `\r` — сброс на начало последней строки (прогресс-бары, tqdm),
`\b` — удаление предыдущего символа. Наверх уходит уже нормализованный текст плюс флаг `replace_last_line`,
чтобы drawer перерисовывал строку, а не добавлял.

## 7. Данные на диске

```
<dir>/.jupyter-out/<notebook-basename>/
  index.jsonl                     # append-only, один объект на прогон
  a3f9/12.parquet                 # <cell-id>/<run-id>.<ext>
  a3f9/12.txt
  b7e1/3.png
```

Запись `index.jsonl`:

```json
{"cell_id":"a3f9","run_id":12,"started_at":"2026-09-03T10:12:04Z","duration_ms":12300,
 "status":"ok","kind":"table","path":"a3f9/12.parquet","rows":1240,"cols":7,
 "code_sha":"9c1f2a","ename":null}
```

- `code_sha` — хэш кода на момент прогона: показывает, что вывод устарел относительно текста ячейки.
- История прогонов = все записи с этим `cell_id`; лимит из конфига (`history_limit`, дефолт 5), старые файлы
  удаляет `outdir.py`.
- `.jupyter-out/` — в `.gitignore`. Документ остаётся чистым текстом, диффы читаемые (§4.6 идеи).
- CLI `jupyter out <file> <cell-id> [--run N]` читает только `index.jsonl` и файл — без nvim и без сайдкара.

### 7.1. Кто сериализует датафрейм (поправка к первой редакции §7)

Первая редакция говорила «сайдкар пишет polars-фрейм файлом». Это невозможно: **сайдкар никогда не видит
фрейм**. Из ядра приходят только mime-бандлы, то есть уже готовый текст и HTML — сам объект живёт в памяти
ядра и наружу не выходит. Отсюда и боль из §4.6 идеи: чтобы прочитать результат, приходилось выковыривать
`data_json` регекспом из HTML.

Значит сериализовать должно само ядро. Механизм (проверен экспериментом):

1. При старте, до того как разрешён первый пользовательский `execute`, сайдкар посылает **скрытую ячейку**
   (`silent=True`, `store_history=False`) с определением `__jupyter_nvim_dump(obj, path)`: проверяет
   `isinstance(obj, pl.DataFrame)`, собирает `LazyFrame`, пишет parquet, возвращает `{rows, cols, schema}`.
   Если polars в ядре нет — возвращает `None`, и ничего не ломается.
2. К каждому `execute` прикладывается
   `user_expressions: {"__jn": "__jupyter_nvim_dump(<result_expr>, '<path>')"}`. Ядро вычисляет это
   **после** ячейки, поэтому `_` уже содержит результат последнего выражения.
3. Ответ приезжает в `execute_reply.user_expressions`. Осторожно: `text/plain` там — **repr питоновского
   значения, а не JSON** (`{'rows': 3, ...}` в одинарных кавычках), поэтому разбор через `ast.literal_eval`.
4. Вернулся словарь — наверх уходит `result` с `kind: table` и путём к parquet вместо текста.

**`result_expr` решает Lua, и это принципиально.** Сайдкар не знает, что такое ячейка и тем более магия
`%%sql`; Lua её разбирает и уже сегодня достаёт имя датафрейма (`molten_table.lua` делает то же).
Дефолт `_` закрывает обычные ячейки, `result_expr: "df"` — путь `%%sql`. Граница §3 не протекает.

Цена: в namespace ядра появляется `__jupyter_nvim_dump`. Осознанно — альтернатива требовала бы правок
в `nb_utils`, то есть связала бы плагин с конкретным пакетом на ядре.

### 7.3. Честность показанного вывода

Один drawer на ноутбук означает, что в окне легко оказывается вывод, который к тексту на экране
уже не относится: подвёл курсор к ячейке — видишь её прошлый прогон. Это ровно тот класс путаницы,
из-за которого §1 идеи вообще написан: вывод выглядит свежим, а он чужой. Поэтому три пометки,
и все три дешёвые:

- **время прогона** — `из истории · 03.09 12:46`. ISO из индекса переводится в локальную зону;
- **`⚠ код изменился`** — sha кода ячейки не совпадает с `code_sha` прогона. Считается той же
  формулой, что в сайдкаре (`sha256(code)[:8]`), поэтому сравнение работает и для истории с диска.
  Это самый сильный признак: он говорит не «вывод старый», а «вывод получен не из этого кода»;
- **`⏳ ещё N`** — где-то идут другие прогоны (§4.3).

Перерисовка висит на `TextChanged`/`TextChangedI`/`InsertLeave`, а не только на смене прогона.
Без этого сравнение работало (оно идёт с буфером, не с файлом), но пометка появлялась лишь когда
что-то ещё вызывало перерисовку — например переход на другую ячейку и обратно. Ответ `is_stale`
кэшируется по `changedtick`: функция зовётся на каждое движение курсора и на каждую правку.

Ошибки хранятся вместе с успешными прогонами: `status: error` плюс `ename` в индексе и трейсбек
в `.txt`. Поэтому «почему вчера упало» отвечается без перезапуска, а `[r`/`]r` позволяют уйти от
неудачной попытки к последнему хорошему результату. Новый запуск снимает просмотр истории.

### 7.2. Где живёт id ячейки (замерено, а не выбрано)

Требование §4.6 идеи: id стабильный и лежит **в тексте**, иначе внешний инструмент не найдёт вывод.
Куда именно его положить, определили четыре замера на живом `Sandbox.ipynb` (65 ячеек):

| гипотеза | результат |
|---|---|
| нативный `id` ячейки nbformat 4.5 | есть у всех 65 ячеек, но `jupytext` **регенерирует все** при обратной конвертации md → ipynb: совпало 0 из 65. Для персистентности бесполезен |
| `cell_metadata_filter=all`, чтобы вынести id в фенс | не помогает, фенсы остаются голыми |
| комментарий в теле ячейки (`# cell-id: ...`) | **опасно**: в `%%sql`-ячейке `#` не комментарий для Redshift, а часть запроса. Сломало бы запрос |
| ключ в info-строке фенса | **работает.** `jncell="a3f9"` доезжает до `.ipynb` честной cell metadata и возвращается дословно. С дефисом (`cell-id=`) jupytext ругается и кладёт значение в `incorrectly_encoded_metadata` |

Итог: `jncell="a3f9"` в info-строке фенса, в percent — на строке маркера. Круг
md → ipynb → md проверен на всех 65 ячейках: **уцелело 65 из 65**, в тело ячеек не протекло
ни одного, `%%sql` остался первой строкой тела. Зафиксировано `jupytext_roundtrip_spec`.

Id детерминирован от содержимого ячейки: несохранённый буфер получит при повторном запуске тот
же id и не потеряет историю. Ячейке без маркера (код до первого `# %%`) записать id некуда —
там остаётся номер ячейки, и история такой ячейки не переживает вставку соседей. Это осознанная
граница, а не недоделка.

**Почему `marks.lua` отложен.** В §5 он стоял рядом с `cellid`, но пока id лежит в тексте,
привязка вывода к ячейке не нуждается в позиции: правка выше не меняет id, а `cells.list`
находит ячейку заново. Extmarks понадобятся на шаге 6, когда появится статус **под ячейкой** —
там нужна именно позиция, переживающая правки. Раньше — лишний слой состояния.

**Чему научили флаки.** Каждый воспроизводился 1 раз на 3–5 прогонов, и все, кроме последнего, оказались
настоящими багами, а не шумом тестов:

| симптом | оказалось |
|---|---|
| первая ячейка без вывода, либо потеряна первая половина | преждевременный `ready`: iopub ещё не подписан (§6.2) |
| `input()` иногда висит навсегда | `input_request` теряется, ROUTER не знает нашу identity (§6.2) |
| `orphan` на чистом прогоне | вывод самого ядра без родителя, не аномалия (§4.5) |
| ядро не поднимается, `KeyboardInterrupt` в импортах | наша же проба stdin прерывала ядро до того, как его цикл ожил (§6.2) |
| редкое падение только под нагрузкой | единственный настоящий шум: тесный бюджет ожидания в тесте |

Ни одного `sleep` в тестах — ожидание всегда по событию или по состоянию. Именно поэтому эти баги падали,
а не прятались: со `sleep` первые четыре выглядели бы как «иногда флачит», ровно как §1 идеи описывает
симптом molten.

**Зелёный тест — не то же самое, что работающая фича.** Трейсбек IPython приезжает списком, внутри
элементов которого есть `\n`, а `nvim_buf_set_lines` такое не принимает. Тест на ошибку в ячейке при этом
проходил: он проверял `run.lines`, а падение случалось асинхронно, в обработчике события. Отсюда правило:
если фича кончается отрисовкой, проверять надо **содержимое буфера**, а не структуру в памяти.
Заодно `ui/common.set_lines` теперь раскладывает многострочные элементы сам — это единственное место,
где текст встречается с буфером, и оно обязано быть непробиваемым.

**Флаки — не шум по умолчанию.** Полезное правило по итогу: тест с живым ядром, падающий 1 раз на 5,
сначала считается багом кода и только потом — багом теста. Из пяти случаев выше четыре были кодом.

**Lua — plenary/busted в headless nvim**, `tests/run.sh`. Состояние: **173 теста** —
`integration_spec` 25, `output_spec` 24, `cells_spec` 19, `exec_spec` 16, `cellid_spec` 15,
`table_spec` 10, `sidecar_codec_spec` 9, `store_spec` 8, `sidecar_live_spec` 6, `kernel_spec` 6,
`jupytext_roundtrip_spec` 2. Вместе с сайдкаром — 232.

`jupytext_roundtrip_spec` гоняет настоящий `jupytext` на копии рабочего ноутбука вместе с
`ipynb_magics.lua` из конфига пользователя (пропускается, если их нет). Это единственная защита
от порчи чужих документов, и она обязана быть автоматической.

`integration_spec` — сквозной: настоящий файл в буфере, настоящее ядро, вывод в drawer'е.
То есть «`%%sql` даёт текст в буфере» проверяется автоматически, без человека.

Важный побочный выигрыш выбора транспорта из §1: Lua-тесты гоняются **против настоящего сайдкара**,
а не против мока — он обычный процесс, и headless nvim умеет его запустить. Поэтому весь async-класс
проблем (колбэки stdout приходят в fast event context, где нельзя трогать API) проверяется без человека:
`sidecar_live_spec` специально вызывает `nvim_buf_set_lines` из обработчика события.

Грабля харнесса, стоившая времени: **`--noplugin` ломает plenary**. С этим флагом не грузится
`plugin/plenary.vim`, команды `:PlenaryBusted*` не существует, и headless nvim просто висит в ожидании
ввода — без единой строки вывода. В `tests/run.sh` флага нет, и это не небрежность.

**Руками остаётся** (§13 моей же оценки: документацией не лечится): virt_text-статус, картинки,
langmapper в русской раскладке, внешняя правка файла во время выполнения ячейки.
