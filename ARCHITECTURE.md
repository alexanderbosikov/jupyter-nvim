# jupyter.nvim — архитектура

Как плагин устроен и почему именно так. Решения записаны вместе с ценой каждого и с тем,
что заставило их принять: большая часть проверена экспериментом, а не выбрана из общих
соображений.

**Имена.** Плагин `jupyter.nvim`, Lua-рут `lua/jupyter/`, команды `:Jupyter*`, сайдкар —
пакет `jupyter_nvim` (не `jupyter`: `import jupyter` уже занят метапакетом), CLI — бинарник
`jupyter-out`, который `jupyter_core` подхватывает как подкоманду родного CLI.

## 1. Решения

| развилка | решение | почему | чем платим |
|---|---|---|---|
| транспорт до ядра | **отдельный процесс, JSON-lines по stdin/stdout** | сайдкар становится обычным процессом, и приёмка гоняется из терминала без nvim. Это главный аргумент, важнее типизированных вызовов | корреляция запрос↔ответ руками, ~40 строк один раз |
| где состояние ячеек | **в Lua** | сайдкар почти stateless: соединение и таблица маршрутизации. Одно место истины при рестарте | ядро не переживает рестарт nvim |
| границы ячеек | **регекспы за интерфейсом детектора** | работают, а интерфейс делает treesitter заменой одного модуля | краевые случаи вроде фенса внутри строки |
| вывод | **один scratch-буфер на ноутбук плюс статус под ячейкой** | вывод копируется, ищется и скроллится штатно; состояние всех ячеек видно сразу | нельзя видеть вывод двух ячеек одновременно |
| id ячейки | **короткий хэш в тексте документа** | вывод находится снаружи редактора, без запуска nvim | первый запуск ячейки правит буфер (одна undo-able правка) |
| интерпретатор | **путь из конфига** | ядро и сайдкар должны быть из одного окружения | нет изоляции зависимостей |

## 2. Процессы и потоки данных

```
┌─────────────────── nvim ───────────────────┐
│  buffer (.py / .md после jupytext)         │
│  cell-id в тексте · статус под ячейкой     │
│  drawer вывода · вкладка таблицы           │
│              lua/jupyter/*                 │
└───────────────┬────────────────────────────┘
                │ JSON-lines (stdin/stdout)
                │ запросы ↓   события ↑
┌───────────────┴────────────────────────────┐
│  jupyter_nvim (python)                     │
│  jupyter_client · router(msg_id) · polars  │
└───────────────┬────────────────────────────┘
                │ ZeroMQ (shell/iopub/stdin/control)
┌───────────────┴────────────────────────────┐
│  ipykernel                                 │
└────────────────────────────────────────────┘

        .jupyter-out/<ноутбук>/   ← пишет сайдкар; читают drawer, CLI, внешние скрипты
```

Три канала, и это осознанно:

- **запросы** — Lua зовёт сайдкар (execute, interrupt, страница таблицы);
- **события** — сайдкар пушит наверх (stream, result, done, состояние ядра);
- **диск** — тяжёлые данные (таблицы, картинки) не идут через пайп вообще, только пути.

## 3. Границы ответственности

**Lua знает:** буферы, ячейки, окна, клавиши, `run_id`, историю прогонов в памяти,
ширину колонок при отрисовке таблицы.
**Lua не знает:** ZeroMQ, структуру jupyter-сообщений, mime-бандлы, polars, parquet.

**Python знает:** протокол ядра, `parent_header.msg_id`, mime-бандлы, polars/parquet,
layout `.jupyter-out/`.
**Python не знает:** номеров строк, буферов, окон. Для него ячейка — только строка
`cell_id`, пришедшая сверху.

Практический тест границы: сайдкар должен полностью работать из
`echo '{...}' | python -m jupyter_nvim`. Если для какой-то фичи это перестаёт быть
верным — граница протекла.

## 4. Протокол

JSON-lines: одна JSON-строка на сообщение, UTF-8. Версия — `v`, несовпадение валится
на `hello` громко, а не тихо в рантайме.

### 4.1. Конверт

```json
// Lua → сайдкар (запрос)
{"v": 1, "id": "7", "op": "execute", "args": {"cell_id": "a3f9", "run_id": 12, "code": "..."}}

// сайдкар → Lua (ответ на запрос: есть id)
{"v": 1, "id": "7", "ev": "ok",    "data": {"msg_id": "3f2c..."}}
{"v": 1, "id": "7", "ev": "error", "data": {"code": "kernel_not_ready", "msg": "..."}}

// сайдкар → Lua (событие: id нет)
{"v": 1, "ev": "stream", "cell_id": "a3f9", "run_id": 12, "data": {"name": "stdout", "ops": [...]}}
```

### 4.2. Запросы

| op | args | ok.data |
|---|---|---|
| `hello` | `{v}` | `{v, version, python, caps[], kernel}` |
| `kernel.start` | `{kernel_name, cwd, env{}, notebook?, out_dir?, history_limit?}` | `{kernel_id, connection_file, kernel_log, attached: false}` |
| `kernel.attach` | то же плюс `{connection_file, pid?}` | `{kernel_id, connection_file, kernel_log, attached: true}` |
| `kernel.state` | — | `{state, since_ms, ...}` |
| `kernel.restart` / `kernel.shutdown` | `{}` | `{kernel_id, aborted}` / `{}` |
| `execute` | `{cell_id, run_id, code, result_expr?}` | `{msg_id}` |
| `interrupt` | `{}` | `{active}` |
| `stdin.reply` | `{value}` | `{}` |
| `table.page` | `{path, offset, limit, cols[]?, order_by[]?}` | `{header[], rows[][], total_rows, offset, truncated, order_by[]}` |
| `ping` | — | `{}` |

`execute` отклоняется, пока ядро не готово: гард встроен в конструкцию, а не прикручен сбоку.
`result_expr` — что сериализовать в parquet, дефолт `_`; для магик Lua присылает имя
переменной (§7.1).

### 4.3. События

| ev | поля data |
|---|---|
| `exec.started` | `{msg_id, started_at}` |
| `stream` | `{name, ops[]}` — список `{op, text}`, где `op`: `append \| replace_last` |
| `display` / `result` | `{kind, mime?, path?, text?, rows?, cols?, schema?}` |
| `exec.error` | `{ename, evalue, traceback[]}` — ANSI снят |
| `exec.done` | `{status, duration_ms, execution_count, user_expressions?}` |
| `clear_output` | `{wait}` |
| `input_request` | `{prompt, password}` |
| `kernel.state` | `{state, reason?, language_version?}` |
| `orphan` | `{parent_msg_id, msg_type}` |
| `log` | `{level, msg}` — `level: kernel` это вывод самого ядра |

`stream` несёт список операций, а не строку, потому что один `\r` в потоке означает
перерисовку строки, а не добавление новой, и решать это должен не UI.

Любое событие может нести `late: true` — прогон, к которому оно относится, уже закрыт.
Отдельного типа события для этого нет намеренно: Lua решает, показать с пометкой или спрятать.

**Прогон закрывается по двум концам.** `idle` приходит по iopub, а `execute_reply`
со статусом — по shell. Это разные каналы, порядок доставки между ними не гарантирован,
а статус ошибки живёт только в реплае. Поэтому `exec.done` уходит, когда получены оба.
Исключение — `aborted`: своего `idle` такой прогон не получит никогда, он закрывается сразу.

### 4.4. Два ключа вместо одного: зачем `run_id`

`cell_id` отвечает на «к какой ячейке», `run_id` — на «к какому прогону». Без второго
ключа вывод, прилетевший из фонового потока после `idle`, приезжает в панель уже второго
запуска той же ячейки. Оба ключа едут в каждом событии; Lua отбрасывает всё, где `run_id`
не равен текущему для этой ячейки.

`run_id` выдаёт Lua (монотонный счётчик на буфер) — так он не теряется при рестарте сайдкара.

**Чего маршрутизация по `msg_id` не лечит** (проверено на ipykernel 7.3):

| когда фоновый поток печатает | что ставит ipykernel в `parent_header` | что видим |
|---|---|---|
| ничего больше не выполняется | msg_id уже закрытой ячейки | правильная ячейка, `late: true` — работает |
| выполняется **другая** ячейка | msg_id текущего запроса | вывод приезжает в чужую ячейку, отличить нельзя |

Второй случай не лечится никаким клиентом: ядро само приписало сообщение не той ячейке.
У браузерного Jupyter поведение такое же. Поведение зафиксировано тестом, чтобы изменение
в ядре не прошло незамеченным.

### 4.5. Инвариант маршрутизации

`active_executions: dict[msg_id, (cell_id, run_id)]` в сайдкаре — единственный источник
привязки. FIFO выводов нет нигде, ни в Lua, ни в Python.

Сообщения не из таблицы делятся на три случая, и смешивать их нельзя:

- **`parent_header.msg_id` указан, но неизвестен** → `ev: orphan`, аномалия: логируем,
  не применяем;
- **`parent_header` пустой** → вывод самого ядра (баннеры и предупреждения на старте).
  Уходит как `log` уровня `kernel`: показать надо, аномалией не считать;
- **служебное** — `status`, `iopub_welcome`, `execute_input`, сообщения внутренних проб
  из §6.2 — молча игнорируются.

## 6. Модули Python (`jupyter_nvim/`)

| модуль | ответственность |
|---|---|
| `__main__.py` | stdio-цикл, проводка `op` → методы сессии |
| `rpc.py` | JSON-lines, диспатч, конверт ошибок, версия протокола |
| `kernel.py` | `jupyter_client`, состояния, готовность (§6.2), рестарт, interrupt, stdin |
| `router.py` | `active_executions`, `msg_id → (cell_id, run_id)`, orphan, закрытие прогонов |
| `mime.py` | mime-бандл → событие: приоритет `text/plain`, картинка файлом |
| `frames.py` | помощник для сериализации датафрейма, разбор ответа, `table.page` |
| `stream.py` | накопление stream-текста с семантикой `\r` и `\b`, снятие ANSI |
| `outdir.py` | layout `.jupyter-out/`, `index.jsonl`, обрезка истории |
| `cli.py` | `jupyter out <файл> <cell-id>` |

### 6.1. Регистрация до отправки

`execute_request` собирается вручную, а не через `client.execute()`: `msg_id` нужен
заранее, чтобы зарегистрировать прогон в роутере **до** отправки. Иначе первое же
сообщение с iopub может приехать раньше своей записи.

### 6.2. Готовность ядра — три канала, а не один

`wait_for_ready` не вызывается никогда: он сыплет `kernel_info_request`, каждый со своей
парой busy/idle в iopub, и при успехе **дренирует весь iopub**, унося вывод уже
запущенных ячеек.

Но и «ответ на shell» готовностью не является. Выяснилось экспериментально: ядро говорило
`ready`, `execute` уходил — и ни одного события в ответ, либо первая половина вывода
терялась. Каждый канал становится рабочим в свой момент:

| канал | тип сокета | чем доказывается готовность |
|---|---|---|
| shell | DEALER→ROUTER, надёжный | ответ на наш `kernel_info_request` |
| iopub | **PUB/SUB** | любое полученное сообщение. Всё опубликованное до установки подписки потеряно безвозвратно — «медленный подписчик» ZeroMQ |
| stdin | DEALER→**ROUTER на стороне ядра** | подтверждённый round-trip: ROUTER не маршрутизирует к identity, которая ещё не подключилась, и `input_request` в это окно теряется молча. Измеренное окно — 50–300 мс |

Готовность = все три. Пока iopub молчит, `kernel_info_request` переспрашивается каждые
150 мс. Маршрут stdin подтверждается настоящим `input()`: скрытая ячейка вызывает его
внутри `except BaseException`, приход `input_request` и есть доказательство, мы отвечаем
пустой строкой. Не пришёл — снимаем `interrupt` и пробуем снова.

Тупиковый путь, который важно не повторить: заранее послать пустой `input_reply`, чтобы
ROUTER узнал identity. Работает в четырёх случаях из пяти, а в пятом приходит **в зазор
между `input_request` и ожиданием ответа**, и ядро принимает его за ответ пользователя:
`input()` возвращает пустую строку. Зависание превращается в молча неверные данные.

**Этапы готовности последовательны.** Сначала ядро доказывает, что его главный цикл жив,
и только потом мы имеем право посылать ему скрытые ячейки и тем более `interrupt`: SIGINT,
прилетевший в ядро, которое ещё импортирует модули, обрывает его собственный старт.

### 6.3. PATH ядра

Kernelspec может задавать интерпретатор относительно (`"argv": ["python", ...]`). Тогда
ядро берётся из PATH, а он у nvim, запущенного из GUI, произвольный — вплоть до того, что
бинарника `python` там нет вовсе, и ячейка падает `ModuleNotFoundError` на первом импорте.
Мы уже знаем нужный интерпретатор — тот, которым запущен сайдкар, — поэтому кладём его
каталог первым в PATH ядра. Абсолютные argv это не затрагивает.

### 6.4. stderr ядра

Уходит в отдельный файл рядом с выводами. Унаследованный stderr означал бы, что
собственные предупреждения ipykernel доезжают до пользователя как ошибки сайдкара,
а настоящие падения тонут в шуме.

### 6.5. Подключённое ядро управляется через pid

Подключение к живому ядру (`kernel.attach`) нужно, чтобы пережить перезапуск редактора:
ядро — не наш потомок, оно спокойно живёт дальше, а в его памяти остаются фреймы, ради
которых и делался долгий запрос.

Обмен сообщениями с чужим ядром ничем не отличается от своего: `load_connection_file`,
`client()`, каналы, тот же путь готовности. А вот управление отличается целиком.
Проверено на jupyter_client 8.9.1:

| вызов | своё ядро | подключённое |
|---|---|---|
| `is_alive()` | как ожидается | всегда `False` — провизионера нет |
| `interrupt_kernel()` | как ожидается | `RuntimeError: No kernel is running` |
| `shutdown_kernel()` | как ожидается | `AssertionError`, ядро остаётся живым |

Поэтому у подключённого ядра живость проверяется сигналом 0, прерывание — `SIGINT`, а
гашение повторяет лестницу jupyter_client вручную: просьба по протоколу, `SIGTERM` на
половине срока, `SIGKILL` в конце. Если этого не сделать, сторож объявит живое ядро
мёртвым на первом же тике, а `kernel.shutdown` тихо оставит процесс в системе.

Перезапуск подключённого ядра — это погасить чужое и поднять своё: провизионера, которым
можно было бы его перезапустить, у нас нет. Аргументы запуска для этого запоминаются при
подключении.

## 7. Данные на диске

```
<каталог>/.jupyter-out/<имя ноутбука>/
  index.jsonl                     append-only, один объект на прогон
  a3f9/12.parquet                 <cell-id>/<run-id>.<ext>
  a3f9/13.txt
  b7e1/3.png
  kernel.log
  runtime.json                    пока ядро живо: pid'ы сайдкара, ядра и редактора
```

`runtime.json` — единственный файл, который живёт ровно столько, сколько ядро. Сайдкар
пишет его при старте и убирает при гашении. Нужен он затем, что nvim не ждёт завершения
сайдкара (иначе выход из редактора стоил бы 1.9 с), а сайдкар может не дожить до гашения
ядра: `SIGKILL`, падение интерпретатора, закрытый терминал. Живой файл при мёртвом
сайдкаре — это ядро без хозяина, и других способов его опознать нет. Проверка ленивая, по
требованию: при открытии ноутбука и в `:checkhealth`, никаких демонов. Опознание — по
пути connection-файла в argv процесса: pid могли выдать заново, и чужое мы не убиваем.

```json
{"cell_id":"a3f9","run_id":12,"started_at":"2026-09-03T10:12:04Z","duration_ms":12300,
 "status":"ok","kind":"table","path":"a3f9/12.parquet","rows":1240,"cols":7,
 "code_sha":"9c1f2a","execution_count":12,"ename":null}
```

- `code_sha` — хэш кода на момент прогона: по нему видно, что вывод устарел относительно
  текста ячейки;
- история ячейки = все записи с этим `cell_id`, лишние обрезаются по `history_limit`;
- пути в индексе относительные, в событиях — полные;
- каталог восстановим прогоном и его место в `.gitignore`.

Читая индекс, обязательно декодировать с `luanil`: иначе JSON `null` приезжает как
`vim.NIL` — userdata, которая истинна и проходит проверку «поле не задано».

### 7.1. Кто сериализует датафрейм

**Сайдкар никогда не видит фрейм**: из ядра приходят только mime-бандлы, то есть готовый
текст и HTML, а сам объект живёт в памяти ядра. Поэтому сериализует само ядро:

1. при старте, до первого пользовательского `execute`, уходит скрытая ячейка
   (`silent`, без истории) с определением функции-помощника: она проверяет тип, пишет
   parquet и возвращает `{rows, cols, schema}`. Нет polars — возвращает `None`;
2. к каждому `execute` прикладывается `user_expressions` с вызовом этого помощника;
   ядро вычисляет его **после** ячейки, поэтому `_` уже содержит результат;
3. ответ приезжает в `execute_reply.user_expressions`. Осторожно: `text/plain` там —
   **repr питоновского значения, а не JSON**, поэтому разбор через `ast.literal_eval`;
4. вернулся словарь — наверх уходит `result` с `kind: table` и путём к parquet.

**Что сериализовать, решает Lua.** Сайдкар не знает, что такое ячейка и тем более магия;
Lua её разбирает и присылает имя переменной в `result_expr`. Дефолт `_` закрывает обычные
ячейки.

Цена: в namespace ядра появляется одна функция с dunder-подобным именем. Альтернатива
требовала бы правок в пакете на стороне ядра, то есть привязала бы плагин к нему.

### 7.2. Где живёт id ячейки

Требование: id стабильный и лежит **в тексте**, иначе внешний инструмент не найдёт вывод.
Куда именно — определили замеры на настоящем ноутбуке (65 ячеек):

| гипотеза | результат |
|---|---|
| нативный `id` ячейки nbformat 4.5 | есть у всех ячеек, но jupytext **регенерирует все** при обратной конвертации: совпало 0 из 65. Для персистентности бесполезен |
| `cell_metadata_filter=all` | не помогает, фенсы остаются голыми |
| комментарий в теле ячейки | **опасно**: в ячейке с магикой языка `#` — не комментарий, а часть кода на этом языке |
| ключ в info-строке фенса | **работает.** `jncell="a3f9"` доезжает до `.ipynb` честной cell metadata и возвращается дословно. С дефисом (`cell-id=`) jupytext ругается и кладёт значение в `incorrectly_encoded_metadata` |

Итог: `jncell="a3f9"` в info-строке фенса, в percent — на строке маркера. Круг
md → ipynb → md проверен на всех 65 ячейках: уцелело 65 из 65, в тело ячеек не протекло
ни одного. Зафиксировано тестом.

Id детерминирован от содержимого ячейки: несохранённый буфер получит при повторном запуске
тот же id и не потеряет историю. Ячейке без маркера (код до первого `# %%`) записать id
некуда — там остаётся номер ячейки, и история такой ячейки не переживает вставку соседей.
Это осознанная граница.

### 7.2.1. Сортировка таблицы

`order_by` — список `{column, desc}` в порядке важности. Сортирует сайдкар, до нарезки
страницы: иначе страница 2 сортировалась бы отдельно от страницы 1 и листание перестало бы
быть согласованным. Полное чтение файла при этом не нужно — `scan_parquet().sort().slice()`
остаётся ленивым.

Накопление сделано на стороне Lua: выбранная колонка встаёт в начало стека, прежние ключи
остаются за ней тай-брейкерами. Повторный выбор той же колонки поднимает её обратно наверх
и меняет направление, а не добавляет дубль. Смена порядка возвращает на первую страницу:
смотреть середину чужого порядка бессмысленно.

Колонку под курсором определяет раскладка, которую форматтер возвращает вместе со строками:
для каждой колонки известно, где она начинается и кончается в экранных клетках.

### 7.3. Честность показанного вывода

Один drawer на ноутбук означает, что в окне легко оказывается вывод, который к тексту на
экране уже не относится. Поэтому три пометки, и все дешёвые:

- **время прогона** — `из истории · 03.09 12:46`;
- **`⚠ код изменился`** — sha кода ячейки не совпадает с `code_sha` прогона. Самый сильный
  признак: он говорит не «вывод старый», а «вывод получен не из этого кода». Перерисовка
  висит на `TextChanged`, ответ кэшируется по `changedtick`;
- **`⏳ ещё N`** — где-то идут другие прогоны.

Ошибки хранятся вместе с успешными прогонами: `status: error` плюс `ename` в индексе и
трейсбек в `.txt`. Поэтому «почему вчера упало» отвечается без перезапуска, а листание
прогонов позволяет уйти от неудачной попытки к последнему хорошему результату.

## 8. Что не поддерживается

ipywidgets, интерактивные виджеты и HTML-таблицы; экспорт вывода обратно в `.ipynb`
и сохранение сессии; удалённый Jupyter-сервер по HTTP; провайдеры картинок кроме
image.nvim; не-Python ядра.

`text/html` в v1: если в бандле есть `text/plain` — берём его; если только HTML —
сохраняем файл и показываем в статусе.

## 9. Тестирование

**Сайдкар — headless pytest против настоящего `ipykernel`**, без nvim. Это и есть причина
выбора JSON-lines. Покрыто: маршрутизация при двух ячейках в очереди, вывод фонового
потока после `idle`, `\r`/`\b`/ANSI, interrupt при очереди, смерть и рестарт ядра,
`input()`, готовность, картинка файлом, `env` до ядра, чистка connection-файла,
результат-датафрейм, чтение вывода без nvim, обрезка истории, таблица на 100k строк.

**Lua — plenary в headless nvim**, `tests/run.sh`. Часть тестов поднимает настоящий
сайдкар и ядро: это побочный выигрыш выбора транспорта — весь async-класс проблем
(колбэки stdout приходят в fast event context, где нельзя трогать API) проверяется без
человека. Отдельный тест вызывает `nvim_buf_set_lines` из обработчика события.

Круг `.ipynb` → markdown → `.ipynb` с настоящим jupytext — единственная автоматическая
защита от порчи чужих документов, и она обязана быть.

Грабля харнесса, стоившая времени: **`--noplugin` ломает plenary**. С этим флагом не
грузится `plugin/plenary.vim`, команды `:PlenaryBusted*` не существует, и headless nvim
просто висит в ожидании ввода — без единой строки вывода. По той же причине
`runtimepath` в `minimal_init` **задаётся**, а не дополняется: иначе тесты исполняют
пользовательский конфиг со всеми его плагинами, и любой блокирующий промпт оттуда вешает
прогон.

### Чему научили флаки

Каждый воспроизводился примерно раз на пять прогонов, и все, кроме последнего, оказались
настоящими багами, а не шумом тестов:

| симптом | оказалось |
|---|---|
| первая ячейка без вывода | преждевременный `ready`: iopub ещё не подписан (§6.2) |
| `input()` иногда висит навсегда | `input_request` теряется, ROUTER не знает identity (§6.2) |
| `orphan` на чистом прогоне | вывод самого ядра без родителя, не аномалия (§4.5) |
| ядро не поднимается, `KeyboardInterrupt` в импортах | своя же проба прерывала ядро до того, как его цикл ожил |
| редкое падение только под нагрузкой | единственный настоящий шум: тесный бюджет ожидания |
| `integration_spec` не доезжал до конца, код 1 без сводки | не флак: дефолтный таймаут plenary (50 с) и интерпретатор без polars |

Ни одного `sleep` в тестах — ожидание всегда по событию или по состоянию. Именно поэтому
эти баги падали, а не прятались.

**Флаки — не шум по умолчанию.** Тест с живым ядром, падающий раз на пять, сначала
считается багом кода и только потом багом теста. Из пяти случаев выше четыре были кодом.

**Зелёный тест — не то же самое, что работающая фича.** Трейсбек IPython приезжает
списком, внутри элементов которого есть `\n`, а `nvim_buf_set_lines` такое не принимает.
Тест на ошибку в ячейке при этом проходил: он проверял структуру в памяти, а падение
случалось асинхронно, в обработчике события. Если фича кончается отрисовкой, проверять
надо содержимое буфера.

## 10. Состояние

Сделано: протокол и сайдкар, выполнение ячеек, вывод в буфер, постраничные таблицы,
стабильные id и история прогонов, статус под ячейкой, картинки, `:checkhealth`,
текстовые объекты, поиск ядер без хозяина и подключение к живому ядру (§6.5).

Дальше по факту использования: режим навигации по ячейкам, отмена отдельного прогона,
пул ядер для параллельных запросов. Очередь работ с оценками — в CONTRIBUTING.md.

Не закрыто:

- почему у буфера ноутбука пропадал `filetype` markdown — не воспроизведено. Промах стоил
  дорого: представление определялось как percent, тот не находил ни одного `# %%` и по
  своему правилу отдавал ядру весь документ одной ячейкой. `M.representation` теперь
  смотрит и в текст, так что цена промаха снята, а на сам случай поставлена ловушка:
  `cells.explain` объясняет выбор, а сессия пишет его в журнал и предупреждает вслух,
  когда представление пришлось угадывать. Когда это повторится, в `:JupyterLog` будет
  видно filetype, число маркеров и фенсов — то, чего не хватало в первый раз;
- пользовательские проблемы, видные снаружи, перечислены в README («Известные проблемы»)
  и здесь не дублируются.
