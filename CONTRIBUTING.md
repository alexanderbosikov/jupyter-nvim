# Как работать над jupyter.nvim

Устройство — в [ARCHITECTURE.md](ARCHITECTURE.md), поведение снаружи — в
[README.md](README.md). Здесь только то, что нужно, чтобы завести проект на чистой машине
и не наступить на грабли, за которые уже заплачено.

## Окружение с нуля

Нужны три вещи: nvim с plenary, python-окружение сайдкара и зарегистрированное ядро.

```sh
# 1. окружение сайдкара (python 3.11+): jupyter_client, polars + pytest, ipykernel
python3 -m venv ~/.venvs/jupyter
~/.venvs/jupyter/bin/pip install -e 'sidecar[dev]'

# 2. ядро с именем python3 — им пользуются тесты
~/.venvs/jupyter/bin/python -m ipykernel install --user --name python3
jupyter kernelspec list   # проверить, что появилось

# 3. plenary для Lua-тестов: любым менеджером плагинов либо руками
git clone https://github.com/nvim-lua/plenary.nvim \
    ~/.local/share/nvim/lazy/plenary.nvim
```

**`argv` кернелспека должен указывать на тот же python, что и сайдкар.** Относительный
путь или другой интерпретатор — и ядро поднимется без `polars`, а результат-датафрейм
молча не соберётся. Это уже стреляло, разбор в §6.3 ARCHITECTURE.md.

## Прогон тестов

```sh
# Lua: headless nvim + plenary. Часть тестов поднимает настоящий сайдкар и ядро.
JUPYTER_NVIM_PYTHON=~/.venvs/jupyter/bin/python ./tests/run.sh
./tests/run.sh tests/cells_spec.lua        # один файл

# сайдкар: pytest без nvim
cd sidecar && PYTHONPATH=. ~/.venvs/jupyter/bin/python -m pytest -q
```

Если plenary лежит не там, где его ищет `tests/minimal_init.lua`, путь задаётся явно:
`JUPYTER_NVIM_PLENARY=/path/to/plenary.nvim ./tests/run.sh`.

`run.sh` сам проверяет интерпретатор до запуска и задаёт plenary таймаут на файл. Раньше
не делал ни того, ни другого, и `integration_spec` тихо не доезжал до конца: без polars он
умирал на третьем тесте, унося сорок с лишним следующих, а при дефолтном таймауте 50 с
родитель бросал ребёнка на полпути. Оба случая выглядели одинаково — код 1, ни сводки, ни
списка падений, — и много месяцев считались флаком прогонщика.

## Стиль

Lua — четыре пробела, двойные кавычки, `---@param`/`---@return` у публичных функций.
Python — аннотации типов, `from __future__ import annotations`. Комментарии на русском и
объясняют **почему**, а не что: «что» видно из кода, «почему» через полгода не
восстанавливается. Шапка модуля описывает его роль и границу ответственности.

## Что значит «готово»

**Зелёный тест — не то же самое, что работающая фича.** Это главный урок проекта, и он
стоил больше всего времени: трейсбек с `\n` внутри элемента списка ронял
`nvim_buf_set_lines` асинхронно, в обработчике события, пока тест на ошибку в ячейке
спокойно проходил — он проверял структуру в памяти. Отсюда правило: **если фича кончается
отрисовкой, тест обязан смотреть в содержимое буфера, а не в промежуточную структуру.**

Второе правило: **флаки — не шум.** Тест с живым ядром, падающий раз на пять, сначала
считается багом кода. Из пяти таких случаев в этом проекте четыре оказались настоящими
багами (таблица в §9 ARCHITECTURE.md).

Третье: часть отказов headless не видит в принципе — картинки, tmux, ширины в терминале,
поведение при смене окон. После изменений, которые их задевают, нужен проход глазами в
настоящем терминале:

1. открыть `.ipynb` — окно вывода на месте, под выполнявшимися ячейками статусы;
2. выполнить python-ячейку, ячейку с магикой языка, ячейку с ошибкой;
3. таблица: `<leader>nt`, страницы `H`/`L`, сортировка `s`/`S`/`c`, номера строк;
4. картинка из matplotlib — переход к другой ячейке, другое окно tmux, другая сессия;
5. история: `[r`/`]r`, перезапуск nvim — выводы на месте;
6. оглавление и переход по нему;
7. прервать долгую ячейку, перезапустить ядро.

## Инварианты, которые держит аудит

Тесты проверяют задуманное поведение; ломалось же всегда на враждебном входе. Классы
ниже в этом проекте уже стреляли, аудит по ним пройден, и **каждый новый код обязан их
держать** — иначе класс заводится заново:

- **чужой текст в буфере.** `nvim_buf_set_lines` не принимает `\n` внутри элемента, а из
  ядра такое приезжает — трейсбек списком, многострочное значение в клетке таблицы.
  Всё, что пишет чужой текст, идёт через `common.set_lines`; вёрстку таблицы держит
  `table.format`, а строковую форму значений — сайдкар (`frames._cell` экранирует
  управляющие символы). NUL, вопреки ожиданию, безопасен: он остаётся NUL и через API;
- **`vim.NIL`.** JSON `null` без `luanil` становится userdata, а она в Lua **истинна** —
  проверка «значение есть» проходит, и в отчёт уезжает `polars vim.NIL`. Любой
  `vim.json.decode` ставит `luanil` для объектов и массивов;
- **ширины и юникод.** Единиц три — байты, символы, клетки экрана, — и путать их нельзя:
  байты рвут кириллицу, символы промахиваются вдвое на эмодзи и CJK. Обрезка одна на
  всех: `common.clip`;
- **границы отказов.** Отсутствие места для записи не должно ломать выполнение: история
  и работа ядра — разные вещи. Сценарии в `tests/boundaries_spec.lua`;
- **гонки отложенных колбэков.** Колбэки stdout приходят в fast event context; доставка
  идёт через `vim.schedule` и под pcall. Между планированием и выполнением буфер могли
  снести — проверяется там же.

## Очередь работ

Порядок — по отношению пользы к риску.

1. **Гранулярный interrupt.** Сейчас прерывание бьёт по ядру целиком, снимая и очередь.
   Отмена одного запроса требует хранить его `msg_id`. Подвох: протокол Jupyter не умеет
   отменять запрос из очереди — только прервать текущий, после чего ядро сбрасывает
   остальные. Значит очередь придётся держать у себя в сайдкаре и отправлять по одной.

2. **Картинки.** Пока их рисует image.nvim, мы управляем чужим состоянием: `state.images`
   не чистится, перерисовка идёт на каждый скролл. Убрать это можно, только забрав
   kitty-протокол себе — свои placement id и удаление по id при смене ячейки. Это не
   починка, а замена слоя, и решение о ней принимает владелец проекта, а не тот, кто
   пришёл чинить баг.
